# C Programming Learning Studio — 단원 제작 공통 가이드 (v1.0)

**대상:** 대학교 1학년 C Programming (GCC C11 기준)  
**적용:** 앞으로 제작·개편하는 모든 C 단원. 기존 Chapter 131–181은 유지하되 개편 시 이 기준을 적용한다.  
**원칙:** 교육 내용이 화면의 개수를 결정한다. *8개 단계, 6개 과제, 3개 학습 구간을 채우려고 내용을 늘리거나 지우지 않는다.*

## 1. 단원 설계 순서 — 내용이 먼저, 화면은 나중

1. **Prerequisites:** 앞 단원에서 이미 배운 내용을 정리한다. 같은 설명을 다시 한 단계로 만들지 않는다.
2. **Outcomes:** 학생이 실제로 확인할 수 있는 학습 목표를 문장으로 작성한다. 예: “배열의 유효 인덱스를 구별한다.”
3. **Core vs Optional:** 1학년이 반드시 배워야 할 최소 사용 역량을 Core로, 심화 API·최적화·특수 상황은 Optional로 구분한다.
4. **Concept map:** 관련 목표는 하나의 단계에 통합하고, 별도 개념·오해가 있는 경우에만 단계를 분리한다.
5. **Worked C example:** 한 단계에 하나의 핵심 판단을 담고, 예상 출력과 그 이유를 설명한다.
6. **Trace/Visualization:** 실행 추적이나 메모리 시각화가 이해를 돕는 경우 사용한다. 시각화는 C 인터프리터가 아니라고 분명히 표시한다.
7. **Check/Transfer:** 출력값 암기보다는 개념을 묻는다. 틀릴 만한 선택지는 실제 오개념에 기반해야 한다.
8. **Coding:** 필수 연습 → 변형 문제 → 실생활/공학 응용으로 설계한다. 과제 수 역시 목표를 기준으로 정한다.
9. **Evidence:** GCC 실행, 브라우저 조작, 모바일 UI, 기존 단원 회귀 검사 후 공개를 결정한다.

## 2. 단계 수는 고정하지 않는다

- 학습 목표마다 독립된 이해·실습·피드백이 필요한 경우 **한 단계를 추가**한다.
- 동일 개념의 수치만 바꾸는 예제나 중복된 API 소개는 **하나로 합친다**.
- 해당 Chapter에 불필요한 주제는 **다음 단원 또는 선택 심화**로 이동한다.
- Core/Optional 구분이 필요한 경우 `coreCount`로 구분한다. 이 값은 **필수 단계 수**이며 필수 단계를 앞에 배치한다.
- 단원별 권장 학습 시간은 `minutes`에 기재하되, 코딩 실습 시간과 구별한다.
- 단계 수는 1, 4, 7, 12 등 **학습 목적에 따라 결정**한다. “최소/최대 8개” 규칙은 없다.
- 코딩 과제 수 또한 **독립적인 역량 검증 필요성**을 기준으로 결정한다.

**현재 참고 사례 (고정 목표 아님)**

| 단원 | 단계 | 판단 |
|---|---:|---|
| 131 Arrays | 7 | 배열 수정은 선언/첨자에 통합, 2차원 배열 및 빈도 계산은 유지 |
| 132 Strings | 7 | 반복되는 strcmp 예제는 통합, 버퍼 안전성은 유지 |
| 133 Standard Library | 6 | rand/srand와 ctype 함수 연결, 중복 strlen은 Strings에 둠 |
| 141 User-Defined Functions | 8 | 원형·호출·값 전달·범위·배열 인수 등 독립 목표 유지 |
| 181 Dynamic Memory | Core 4 + Optional 4 | malloc/free 중심, calloc/realloc 및 디버깅은 선택 |

## 3. 데이터 스키마와 기존 플랫폼의 연결

단원별 파일: `c-programming/<slug>/data.js`에 **`window.C_JOURNEY = { ... }`** 객체를 작성한다. 실습 엔진은 `c-programming/journey.js`, 코딩 편집기는 `c-programming/practice-engine.js`를 공용으로 사용한다.

주요 데이터 필드:

- `slug`, `title`, `book`, `summary`, `related`, `relatedTitle`
- `lessons`: **가변 길이 배열**. 실제 단원 학습 단계 수를 결정한다.
- `practice`: **가변 길이 배열**. 실제 코딩 과제 수를 결정한다.
- `phases`: 학습 흐름에 필요한 Before/In/After 설명(기존 UI는 세 구간). **3개 개념 단계가 아니라 3개 학습 활동 구간**으로 사용한다.
- `phaseBreaks: [a,b]`: 선택 항목. 0부터 시작하는 단계 인덱스 기준으로 Before/In/After 구간을 나누는 경계. Core/Optional과 독립이다.
- `coreCount`: 선택 항목. `0 < coreCount < lessons.length`인 경우 **필수/선택 심화** 분리.
- `contentRevision`: 학습 단계의 추가·삭제·순서 변경 시 증가. 과거 브라우저 진도와 새 단계 인덱스가 뒤섞이지 않게 한다.
- `authoringVersion: 1`: 이 공통 제작 가이드를 준수하는 새 단원의 식별자.

각 `lessons[i]`는 다음을 권장한다.

| 필드 | 목적 |
|---|---|
| `title`, `goal`, `concept` | 독립된 학습 목표와 직관적인 설명 |
| `code`, `predict`, `output` | **실제 GCC C11 코드**, 예상 출력 |
| `trace` | 실제 코드에서 매칭되는 문장과 상태·의미 |
| `quiz: {q,options,correct,explain}` | 맞힐 수 있는 근거가 있는 개념 질문 |
| `transfer`, `guide` | 응용 질문과 교수자 해설 |
| `model` | 필요한 가상 실험을 명시. 실제 C 실행과 구분 |
| `minutes` | 개념 학습 권장 시간(선택) |

**단계 수와 과제 수에 대한 숫자 제한은 공통 제작 규칙에 두지 않는다.** 런타임의 동작상 `lessons`는 비어 있을 수 없으며, 직접 코딩을 하는 단원에는 의미 있는 `practice`를 제공한다.

## 4. 1학년에게 맞는 설명과 정확성

- 교육 용어는 **영어 기술 용어 + 자연스러운 한국어 설명**으로 제시한다.
- 한 단계에 “무엇을 알아야 하나 / 어디에서 쓰나 / 어떤 코드를 읽나 / 어떤 오류를 피하나”가 드러나야 한다.
- 예제는 별도 입력 없이 실행되도록 만들거나 입력 조건과 예상 입력을 명시한다.
- `#include`, 서식 지정자, 자료형, 널 종료 문자, 함수 프로토타입과 호출 순서를 GCC C11에서 확인한다.
- UB(정의되지 않은 동작)는 **실행을 요구하지 않고** 그림이나 안전한 비교 코드로 설명한다.
- `sizeof`/주소/난수 출력 등 구현 의존 값을 특정 숫자로 고정하지 않는다.
- `rand`는 학습용 의사난수이고 보안용이 아니며, `% n` 편향 가능성을 설명한다.
- `fgets`의 반환값과 개행 처리를 주의한다. 파일 경로·문자 인코딩·플랫폼 차이를 명시한다.
- 엔진의 `model`은 개념 시뮬레이션이다. 코드가 실제 실행되는 것처럼 주장하지 않는다.
- 시각화가 이해에 도움이 되지 않을 때 **개념만 보여 주는 중복 실험**을 만들어 강요하지 않는다. 새 런타임 기능이 필요하다면 안전한 선택형 컴포넌트로 확장한다.

## 5. 신규 단원 제작 절차

1. `c-programming/_template/data.js`를 바탕으로 데이터 파일 작성(템플릿의 2단계는 예시일 뿐 목표 개수가 아님).
2. 가장 가까운 기존 단원 `index.html`과 `practice/index.html`을 가져와 제목·상대 경로·스크립트 참조만 변경한다.
3. 학습 목표별로 단계와 과제를 만들고, **개념 → 코드 → 추적 → 확인 → 응용**의 연결을 점검한다.
4. `course-catalog.json`에 Chapter ID / 이름 / 그룹 / URL을 등록하되, **처음에는 `published:false`**로 둔다.
5. `node tests/c-authoring-policy.mjs`로 공통 스키마 검사; `node tests/c-course-gcc.mjs`로 GCC 예제·출력 검증.
6. GitHub Actions 또는 실제 브라우저에서 모바일·데스크톱 학습 메뉴와 코딩 편집기를 점검한다.
7. 검토·테스트 이후 통합 관리자에서 공개 전환한다. 공개는 메뉴 표시 제어이지 직접 URL 접근 차단이 아니다.

## 7. 점검 시스템의 구분

- **스키마 검사:** 누락된 필드·잘못된 경로·핵심 단계 구조를 발견 (실행 정확도 보장 아님)
- **GCC 실행 검사:** C11 참조 코드와 출력 확인 (모든 입력에서의 올바름까지 보장하지 않음)
- **브라우저 QA:** 메뉴·진도·화면·실험 상호작용 검증 (학습 효과 자체를 증명하지 않음)
- **교수자 검토:** 개념 정확성·중복·난이도·사용 가치 판단. **자동 테스트로 대체할 수 없다.**

> 과제 개수, 단계 개수, 실습 모델의 개수보다 학생이 실제로 이해하고 사용할 수 있는 역량을 우선한다.

## 7. 공통 UI/UX 품질 및 회귀검사 (2026-11 보강)

현재 공개된 공통 학습 엔진 단원 7개(131·132·133·141·151·161·181)는 `c-programming/journey.js`를 공유하며 File I/O(171)는 별도 엔진을 사용한다. **동일한 교육 원칙을 적용하되, 기존 학습 기록 키나 예제 의미를 변경하지 않는 것**을 우선한다.

1. **제목 일치:** 왼쪽 단원 메뉴의 항목 이름과 오른쪽 해당 학습 단계의 `h2`는 같은 데이터 필드 `lessons[i].title`에서 파생한다. 단계 수는 가변이고 과거 진도 인덱스는 보존한다.
2. **코드 표시:** `lessons[i].code`는 가능한 전체 GCC C11 프로그램으로 표시하고 `#include`, `main`, 출력 결과를 함께 보여준다. `practice[i].starter`는 작성이 필요한 **미완성 Starter Code**라고 별도로 명시한다. 동작할 수 없는 코드 조각을 전체 프로그램처럼 표시하지 않는다.
3. **질문 설명:** 상황·학습 목표(`quiz.context`를 지정한 경우 우선, 그렇지 않으면 `goal`) → 질문 → 선택지 → 답안 확인 → 근거 해설 순서로 구성한다. 형식상 반복되는 '상황 설명 상황:' 같은 장식 문구를 피한다.
4. **언어 모드:** 영어 모드에서는 안내 문장과 버튼·학습 결과에 한국어가 섞이지 않아야 한다. `en.js`의 `lessons[i]`에 goal, concept, predict, transfer, guide, quiz(q/options/explain)을 제공한다. 출력 결과·C 코드·학생 답안은 의미를 임의로 번역하지 않는다.
5. **필수와 심화:** `coreCount`와 `practiceCoreCount`가 정한 경계를 메뉴와 진행률에 정확히 반영한다. 학생이 선택 심화 과정을 완료하지 않아도 필수 학습 진행이 가능해야 한다.
6. **화면 가독성:** 짧은 코드라도 세로 높이 제한 때문에 전체 예제가 잘리지 않게 하며, 좁은 화면은 코드/설명 패널을 세로로 배열한다. C 소스에서 연산자 등호나 비교 연산자를 합자(ligature)로 묶어 표시하지 않는다.
7. **기존 기능 보호:** `els-journey-<slug>-v<revision>`, `els-concept-<slug>-v<revision>` 저장 키와 트레이스·모델·코드 편집기 기능을 유지한다.

**정적 검사:** `node tests/c-course-ui-consistency.mjs`는 현재 공개된 공통 엔진 단원 전체에 대해 위의 데이터 계약과 출력 조건을 검사한다. `node tests/c-fileio-ui.mjs`는 독립적인 File I/O 페이지를 확인한다. **실행 정확성:** `node tests/c-course-gcc.mjs`. 정적 검사는 실제 PC·모바일 브라우저 QA를 대체하지 않는다.
