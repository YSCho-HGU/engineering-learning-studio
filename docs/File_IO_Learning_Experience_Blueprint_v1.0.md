## 1. Driving Question과 학습 성과

### 프로젝트의 중심 문제

센서 시스템을 재시작했더니 이전에 측정한 값들이 사라졌다. 시간과 측정값을 파일로 안전하게 저장하고 재시작 후 복원하며, 잘못된 데이터나 파일 오류를 확인하고, 임계값을 초과한 측정값을 별도 파일로 기록하는 C 프로그램을 개발하라.

이 하나의 사례를 계속 발전시키되, 학생이 한 함수만 외우도록 만들지 않는다.

## 4. Mission별 상세 설계와 오개념

### M1 — Persistence (§7.1)

**오개념**: 재시작하면 변수 값도 자동 복원된다; 파일을 여는 동작 자체가 현재 메모리를 저장한다.

**활동 흐름**:
1. 실행 중 변수 score와 파일 scores.txt의 상태 제시.
2. 종료 후 각각 어떤 값이 남는지 예측.
3. 종료/재시작을 실행하고 차이 확인.
4. 왜 다른지 1~2문장으로 설명.
5. 값을 파일에 기록하지 않은 변형 상황에 적용.

**통과 증거**: 초기 예측의 정확도 자체보다 관찰 후 인과 관계를 설명하고 새로운 상황에서 구분할 수 있는지 평가.

### M2 — Stream와 FILE * (§7.2)

**오개념**: FILE *에는 파일 이름 문자열이 저장된다; stdout/stderr는 같은 출력 목적; printf와 fprintf는 연결이 없다.

**활동 흐름**:
1. 입력/정상 출력/오류 출력/파일 저장의 4가지 요구사항 제시.
2. stdin, stdout, stderr, FILE *fp 중 알맞은 Stream을 연결.
3. printf와 fprintf(stdout, ...) 비교 및 scanf와 fscanf(stdin, ...) 비교.
4. fopen 실패 시 fp == NULL 검사 이유 설명.

**증거**: 목적에 맞는 Stream 선택과 라이브러리 관리 Stream을 가리키는 FILE * 의미 설명.

### M3 — fopen, mode, path (§7.3)

**예제 파일**: readings.txt는 한 줄에 double 하나인 25.0, 26.5 두 줄.

**예측 질문**:
- 기존 파일을 r/w/a 각각으로 열면?
- w로 성공적으로 열고 곧바로 프로그램을 다시 시작하면?
- a로 열고 fprintf를 호출한 후 파일 내용은?
- 존재하지 않는 파일을 r로 열면 fp는?
- 실행 working directory가 달라지면 상대 경로는 어떻게 해석되는가?

**실행 상태 모델**:
~~~text
CLOSED -- successful fopen --> OPEN(mode, position)
OPEN(r) -- successful fgets --> position advanced; optional fputs stdout
OPEN(r) -- fgets returns NULL at EOF --> READ_DONE
OPEN(w/a) -- successful fprintf --> WRITE_DONE; file modified
READ_DONE / WRITE_DONE -- fclose --> CLOSED; file remains
RESTART PROGRAM --> process state reset; file remains
RESET LAB --> teaching-only reset; original sample restored
~~~

**오개념**: w는 기존 파일을 유지한다; Restart가 truncate된 파일을 복원한다; 마지막 값을 읽자마자 EOF 플래그가 항상 선다.

**핵심 UX**: r 모드에서는 r 코드와 읽기 버튼만 표시. w/a에서는 쓰기 코드와 쓰기 버튼만 표시. 버튼을 누르면 실제 화면에 표시된 문장과 실행 순서가 일치해야 한다. 이전 사이트에서 발생한 혼란을 재발시키지 않는다.

**증거**: 4개 예측, 상태 변화 설명, 안전한 append 예제 작성.

### M4 — Text I/O, EOF, malformed data (§7.4)

**오개념**:
- fscanf의 반환값이 읽은 숫자 자체다.
- 파일 끝을 미리 feof로 확인하면 읽기 성공을 보장한다.
- fgets는 버퍼 크기와 관계없이 한 번에 한 줄 전체를 읽는다.
- EOF와 숫자 변환 실패는 같은 조건이다.

**세 실험**:
A. 데이터 단위에 따라 fscanf/fgets/fgetc, fprintf/fputs/fputc 선택.  
B. numbers.txt 정상 정수 10/20/30에서는 fscanf("%d")가 1,1,1,EOF.  
C. 10/ABC/30에서는 성공 1회 뒤 matching failure 0; 이 경우 feof가 0일 수 있다. 빈 파일에서는 첫 읽기 EOF; 실제 Stream 오류는 ferror로 구분.

**코드 패턴(독립적으로 실행되는 완성 예제가 아닌, fopen에 성공한 fp가 있다는 전제의 조각)**:
~~~c
int x, rc;
while ((rc = fscanf(fp, "%d", &x)) == 1) {
    printf("%d\n", x);
}
if (ferror(fp)) {
    /* I/O failure */
} else if (!feof(fp)) {
    /* conversion mismatch */
} else {
    /* clean EOF */
}
~~~

**추가 실험**: 80-byte 버퍼에 100자 줄을 전달하여 fgets의 읽기 길이와 줄 경계를 확인.

**증거**: 세 반환값 상황을 구분하고, 잘못된 반복 조건을 고치며, 올바른 이유를 설명.

### M5 — Structure Records (§7.5.1–7.5.2)

**레코드 형식**: students.txt = 정수 ID, 공백 없는 이름, 실수 점수. 예: 101 Mina 92.5.

**학생 흐름**:
1. Structure 멤버 ↔ text file 필드 순서 매핑.
2. 저장 전 텍스트 예측.
3. 실제 파일에 직렬화; 그 후 입력 폼과 메모리 값을 변경해도 파일은 그대로임을 확인.
4. 다시 파일 텍스트를 읽어 구조체를 복원. 기존 메모리 객체 복제는 금지.
5. fscanf의 성공 변환 개수 3 검사, 이름 버퍼 크기, 배열 최대 용량, 잘못된 행 확인.
6. saveRecords / loadRecords 함수로 분리.

**증거**: Round-trip 값 일치, 비정상 레코드 진단, 올바른 자원 해제.

### M6 — Sensor Logger (§7.5.3)

**전제 데이터셋(시범용, 교재 실제 수치라고 단정하지 않음)**: sensor_log.txt의 시간–측정값 쌍.

~~~text
0.0 2.51
0.1 2.55
0.2 2.48
0.3 3.82
~~~

**학생 활동**:
1. 임계값 3.0일 때 평균/경보 개수를 예측.
2. fscanf("%lf %lf")로 2개 변환 성공을 검사.
3. 출력 결과 및 alerts.txt와 비교.
4. 형식이 잘못된 행, 빈 파일, 파일 없음, 쓰기 실패 등 오류 입력 실험.
5. 센서의 측정값, 단위 및 형식을 명시하여 다른 데이터 형식으로 확장.

**증거**: 실제 GCC 실행 결과, stdout/stderr/alerts.txt, 정상·비정상 테스트, 오류 원인 설명.

### M7 — P1–P6 Coding Practice (§7.7.3)

| 과제 | 교재 요구사항 | 추가 테스트 설계(제안) |
|---|---|---|
| P1 | 정수 5개를 numbers.txt에 한 줄씩 저장 | 부정확한 정수 입력, overwrite |
| P2 | values.txt의 double 평균과 개수 출력 | 빈 파일, 형식 오류, 나눗셈 방지 |
| P3 | input.txt를 fgets/fputs로 copy.txt에 복사 | 개행 없는 마지막 줄, 긴 줄 |
| P4 | Student 구조체 배열을 fprintf로 저장 | 멤버 순서, 파일 형식 |
| P5 | Student 레코드를 fscanf가 3이 아닐 때까지 읽고 최고 점수 | 최대 용량, 깨진 레코드, 빈 파일 |
| P6 | time/value에서 threshold 초과 값을 출력하고 alerts.txt 기록 | 임계값 경계, 출력 파일 내용, 오류 데이터 |

**Scaffolding 축소 규칙**: P1–P2는 Starter Code와 단계적 힌트, P3–P4는 함수 구조 중심, P5–P6는 요구사항과 테스트만 제공하는 방향을 권고. 이는 교재 원문 규칙이 아니라 교육 설계상 제안이다.

**정답 판정**: 정규식 문자열 검색을 PASS라고 부르지 않는다. 실제 컴파일, 종료 코드, stdout/stderr, 생성 파일, 오류 조건을 별도로 확인한 뒤에만 수행 결과로 인정.

### M8 — Transfer & Reflection (§7.7.4–7.7.6)

**독립 문제 예시**: 센서값 대신 Student 성적 레코드를 저장·복원하며, 비어 있거나 깨진 파일에 대응하는 Persistent Record Manager 개발.

**학생 설명 항목**: 파일 형식과 모드 선택 이유, 예측과 실제 결과의 차이, 테스트로 발견한 오류, AI 조언 중 수용/거부한 이유, Python 데이터 분석으로 연결하려면 필요한 형식 규칙.

**독립 성취**: 힌트 없는 새 문제, 실행 증거, 짧은 설계 설명. 1–2주 뒤 지연 평가 권장.

## 6. AI Coach: 문제 해결 능력을 대체하지 않는 지원

- **Independent**: 생성형 힌트 없이 시도. 필요 시 실제 컴파일 오류와 승인된 교재 자료만 이용.
- **AI Coach**: 학생의 최초 시도와 테스트 결과에 기반한 단계적 힌트. 완성 정답은 정책에서 허용한 복습 단계에만 제공.
- **AI Co-Engineer**: 심화 프로젝트에서 AI 코드 생성과 리뷰 허용. 학생은 생성 코드의 테스트와 설계 판단을 기록.

**단계적 힌트 예시 — fscanf 조기 종료**
H1. 마지막 읽기의 실제 반환값은?  
H2. 변환 형식은 몇 개의 값을 요구하는가?  
H3. 어느 입력 행에서 기대 형식이 달라지는가?  
H4. EOF와 형식 오류는 어떻게 분리하여 확인할 것인가?  
H5. 필요할 때만 관련 예제 또는 정답 공개(교수자 정책).

**AI 운영 원칙**: 테스트 결과를 AI가 만들어내지 않는다. 학생 개인정보·비밀값을 모델 프롬프트에 넣지 않는다. AI가 사용 불가능해도 기본 학습 과정은 진행 가능해야 한다.

## 7. 성취 평가와 직접 증거

### 3개 학습 상태와 1개 인증 단계
- Participation: 페이지와 활동에 참여.
- Concept Check: 예측과 설명의 정확성 확인.
- Implementation Check: 컴파일과 정상 입력 테스트 통과.
- Mastery Verified: 새로운 상황의 독립 구현·실패 진단·설명까지 통과.

### 제안 루브릭 (100점)
| 평가 축 | 비중 | 관찰 증거 |
|---|---:|---|
| 개념 이해 | 20 | Stream, 모드, EOF, 반환값 설명 |
| 예측·인과 설명 | 20 | 결과 예측 및 차이 원인 설명 |
| 구현 | 25 | 올바른 C 코드, 포맷, 자원 정리 |
| 검증·오류 진단 | 25 | 정상/빈 파일/형식 오류/경계 입력 테스트 |
| 전이 | 10 | 새 데이터/요구사항에 독립 적용 |

이는 기존 Master Plan과 맞춘 초기 평가안으로, 학교의 확정 성적 평가 방식이 아니다.

### 시범 평가
- 사전/사후 평가에 같은 문항을 재사용하지 않고 난이도가 비슷한 다른 문항 사용.
- 1–2주 뒤 지연 평가 포함.

- 5–8명의 대표 학생과 사용성 관찰을 먼저 수행.
- 교수자 평가의 일치도와 학습 성과를 확인한 뒤 다른 과목으로 확장.

## 8. 구현에 필요한 데이터셋과 정확성 게이트

| 데이터 ID | 파일 | 형식 | 주요 활동 |
|---|---|---|---|
| DS-A | readings.txt | double 한 열 | M3 모드 |
| DS-B | numbers.txt | integer 한 열, 오류 토큰 변형 | M4 EOF |
| DS-C | students.txt | int ID, name(공백 없음), double score | M5, P4–P5 |
| DS-D | sensor_log.txt | double time_seconds, double measurement | M6, P6 |
| DS-E | alerts.txt | 출력 경보 텍스트 (형식 명시 후 생성) | M6, P6 |

**정확성 원칙**
1. 실행 가능이라고 표시된 C 코드는 독립적인 완전 코드로 작성하고 실제 컴파일로 검증.
2. 브라우저 모의 실행은 SIMULATED로 명시. 검증되지 않은 OS/Stream 동작을 사실처럼 묘사하지 않음.
3. 읽기 성공 검사와 feof/ferror 원인 진단을 구분.
4. fgets는 버퍼 크기 안에서만 읽으며, 항상 완전한 줄을 보장하지 않음.
5. 각 실험의 초기 파일 내용, 종료·재시작, 샘플 복원은 별도 개념으로 설명.
6. 현재 작업 디렉터리·경로·파일 포맷·개행 규칙을 문서화.
7. 테스트 결과는 실제 컴파일러/실험 엔진의 값이거나 교육용 참조 출력임을 명시.

## 9. QA 수용 조건과 UI/UX 체크

**교육 수용**
- 각 Mission에 학습 목표, 주요 오개념, 예측 질문, 실제 관찰, 설명 활동, 적용 문제가 있어야 함.
- 단순 클릭/객관식 완료는 코딩 숙달 인증에서 제외.
- 정답 공개 시점과 단계적 힌트는 의도대로 제어.
- 교재의 관련 절과 실제 실습 간 연결을 확인할 수 있음.

**기술 수용**
- C 언어 !=/== 및 서식 정확성, code ligature 비활성화, line number, 가독성 대비 확보.
- 하나의 C 프로그램 경로와 버튼 조작이 일치(잘못된 모드에서 타 함수 조작 없음).
- GCC C11 컴파일(실제 사용 버전 명시), 정상·비정상 실행 결과 회귀 테스트.
- 정규식 점검은 단순 구문 점검이라고 명시. 정답/컴파일 판정과 분리.
- 모바일/데스크톱, 키보드, 스크린리더 접근성 확인.
- 학생 계정·개인 학습 기록의 중앙 저장은 권한·보존·삭제 정책 결정 후에만 도입.

**출시 게이트**
- 주요 실행 흐름 오류 0건.
- 모든 학습 목표가 최소 한 가지 직접적인 학습 증거와 연결.
- 주요 학생 혼란 구간의 사용성 평가 완료.
- File I/O가 기준 모듈로 검증되기 전에는 다른 교과목에 동일 UI를 대량 복제하지 않음.

## 11. 권장 첫 번째 실제 구현: M3와 M4의 Vertical Slice

현재 전체 8개 Mission을 즉시 모두 재작성하는 것보다 **M3(파일 모드) + M4(읽기 결과·EOF)**를 먼저 완성형으로 제작한다.

수직 시제품에는 문제 제시 → 예측과 이유 → 실제 실행(또는 검증된 모의실험) → 파일 상태/반환값 시각화 → 오류 진단 → 간단한 C 코드 작성 → 새로운 입력 테스트 → 실제 학생 관찰을 모두 포함한다.

이 두 모듈이 기술적으로 정확하고 교육적으로 효과적임이 확인되면 같은 원칙으로 M1–M8을 구현한다. 기존 8단계 웹 코스와 P1–P6 페이지는 보존하면서 교체 여부를 단계적으로 결정한다.
